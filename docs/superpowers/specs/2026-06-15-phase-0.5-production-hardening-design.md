# SMS Backend — Phase 0.5 Production Hardening (Design Spec)

> **Status:** Approved design (2026-06-15). Bridges the gap between the green Phase 0 foundation
> and a safely deployable, horizontally-scalable API — **without adding any business endpoints**.
> Builds directly on `docs/superpowers/plans/2026-06-15-backend-phase0-and-roadmap.md` (Phase 0)
> and `docs/superpowers/specs/2026-06-15-backend-stored-procedures-design.md` (master delta spec).
> This is a focused pull-forward of selected Phase 6 concerns that are unsafe to defer once
> business endpoints multiply the attack/scale surface.

## Context

Phase 0 is complete and verified green (20/20 tasks; build clean; 22 unit + 6 integration tests
passing against the real dev SQL Server `DESKTOP-TJL4SG6`; tenant RLS isolation proven; DB connects).
An end-to-end audit (2026-06-15) found the foundation **runnable but not production-deployable**: five
"red" gaps block any real deploy, and two "yellow" auth shortcuts are security-relevant enough to fix
before Phase 1 adds roles-driven business logic. This spec closes all seven.

**Decisions locked during brainstorming (2026-06-15):**
- **Migrations in prod:** a dedicated **CLI runner** in `db/Sms.Migrations`, invoked by CI/CD before
  rollout. Startup migration stays **dev-only**. Chosen for horizontal scale-out safety (no boot-time
  migration races across API instances).
- **Scope:** the **5 red gaps + 2 yellow auth fixes** (7 items). Transport hardening (HSTS/HTTPS
  redirect) explicitly **out of scope** for this pass — stays Phase 6.
- **Secrets:** **environment variables in prod + `dotnet user-secrets` in dev**, with a **fail-fast
  boot guard**. Cloud-agnostic; consistent with "no cloud binding until Phase 6."

**Non-goals:** no business endpoints; no new tables beyond what the two auth procs need (none — they
read existing `Users`/`UserRoles`); no managed-service binding; no transport-layer hardening; no
frontend changes.

## Items

### Item 1 — Production migration path (CLI runner)

**Problem.** `MigrationRunner.Run()` fires only when `app.Environment.IsDevelopment()`
(`src/Sms.Api/Program.cs`). There is **no production migration path** — a prod deploy would hit an
unmigrated database. The master spec (§1.4) says "applied … via CI job in prod"; that job does not exist.

**Design.**
- Convert `db/Sms.Migrations` to also produce an executable: add `<OutputType>Exe</OutputType>` and a
  top-level `Program.cs` entrypoint. The project remains referenced as a library by `Sms.Api` (an exe
  assembly is still referenceable), so the existing dev-startup path is unchanged.
- The entrypoint resolves the connection string in this order: `args[0]` → env `ConnectionStrings__Sql`.
  If neither is present, it prints a usage message and exits non-zero. On success it calls the existing
  `MigrationRunner.Run(conn)`, prints the applied migration versions, and returns exit code 0; any
  exception is logged and returns a non-zero exit code (so CI fails loudly).
- Invocation: `dotnet run --project db/Sms.Migrations -- "<connectionString>"`
  (or with `ConnectionStrings__Sql` set and no arg).
- **Idempotence:** re-running applies nothing new (`CREATE OR ALTER` procs + FluentMigrator version
  table) — a second run is a clean no-op. This is asserted in CI.
- `src/Sms.Api/Program.cs` keeps its `if (IsDevelopment()) MigrationRunner.Run(conn)` block unchanged;
  prod never migrates on boot.
- **CI:** add a job/step to `.github/workflows/ci.yml` that, against the SQL service container, runs the
  CLI **twice** — first to migrate, second to prove idempotence (no error, no new versions).

**Acceptance.** CLI migrates a fresh DB; second run is a no-op; non-zero exit on bad/missing connection
string; `Sms.Api` still migrates on dev startup and never in Production.

### Item 2 — Secrets fail-fast

**Problem.** `appsettings.json` ships a usable-looking placeholder JWT signing key
(`"CHANGE-ME-in-user-secrets-at-least-32-bytes-long!!"`) and a hardcoded dev connection string
(`Server=DESKTOP-TJL4SG6;…`) in the **base** (prod-fallback) file. Nothing prevents the API from booting
with the placeholder key — a critical auth weakness if it ever reaches prod.

**Design.**
- New `SecretsValidator` (in `Sms.Shared.Kernel`, e.g. `Configuration/SecretsValidator.cs`) with a
  `Validate(JwtOptions jwt, string? connectionString)` that throws a clear exception when:
  - `jwt.SigningKey` is null/empty, **equals the known placeholder**, or is **< 32 bytes** (UTF-8); or
  - the connection string is null/empty.
- Invoke it in `src/Sms.Api/Program.cs` immediately after binding config and **before `builder.Build()`
  / `app.Run()`** so a misconfigured process exits at startup rather than serving traffic with a weak key.
- **Config sourcing:**
  - **Base `appsettings.json`:** `Jwt:SigningKey` set to empty string (`""`) — no usable secret in source
    control. The hardcoded `DESKTOP-TJL4SG6` connection string is **removed** from base
    `appsettings.json`.
  - **`appsettings.Development.json`:** keeps the dev `DESKTOP-TJL4SG6` connection string and a dev-only
    signing key (≥ 32 bytes, not the placeholder) so local dev runs without extra setup; alternatively
    `dotnet user-secrets` for the key (documented in the implementation plan).
  - **Production:** `ConnectionStrings__Sql` and `Jwt__SigningKey` supplied via environment variables
    (matches `docker-compose.yml`, which already sets `Jwt__SigningKey`).
- The guard runs in **all** environments; dev satisfies it via Development config, prod via env vars.

**Acceptance.** Boot throws when the key is missing/placeholder/too short or the connection string is
absent; boots normally with a valid key + connection string; no usable secret remains in base
`appsettings.json`.

### Item 3 — Global exception handler → standard error envelope

**Problem.** No global exception handler. An unhandled exception returns a default framework 500 (or a
leaked stack in dev), not the standard snake_case `{ error: { code, message, details } }` envelope the
spec mandates everywhere.

**Design.**
- Implement `IExceptionHandler` (e.g. `Sms.Shared.Kernel/Http/GlobalExceptionHandler.cs`) registered
  via `builder.Services.AddExceptionHandler<GlobalExceptionHandler>()` + `app.UseExceptionHandler()`,
  placed **first** in the middleware pipeline.
- On any unhandled exception: log the full detail via Serilog (with the trace id), then write
  **HTTP 500** with the existing `ErrorEnvelope` shape: `code = "internal_error"`, a **generic** message
  (no stack trace, no exception text leaked to the client), `details = null`. Response uses the same
  snake_case JSON options as the rest of the API.
- Honours the configured `ProblemDetails`/content negotiation only insofar as it always emits our
  envelope shape for consistency with the frontends' error contract.

**Acceptance.** A handler that throws yields a 500 whose body is the snake_case error envelope with
`code: "internal_error"` and no leaked internals; the exception is logged server-side with correlation.

### Item 4 — Real `/health/ready` readiness probe

**Problem.** `/health/ready` returns a static `{ status = "ready" }` without touching the database — it
reports healthy even when SQL is unreachable, which is useless (and dangerous) as a load-balancer/k8s
readiness gate.

**Design.**
- Keep `/health` static (liveness — "process is up").
- Wire `/health/ready` to a real check via `builder.Services.AddHealthChecks()` with a small custom
  check that opens a **plain** `SqlConnection` from the configured connection string and runs
  `SELECT 1`. Crucially this check **does not** go through `SqlConnectionFactory`/`SESSION_CONTEXT`
  (readiness is tenant-agnostic and must not require a tenant context).
- Map `/health/ready` to that health check: **200** `{ status: "ready" }` when the query succeeds,
  **503** `{ status: "unavailable" }` when it fails. Response stays snake_case.

**Acceptance.** `/health/ready` returns 200 when the DB is reachable and 503 when it is not; `/health`
stays static and always 200 while the process lives.

### Item 5 — CORS + rate limiting

**Problem.** The master spec lists CORS and rate-limiting as Phase-0 cross-cutting foundations, but
neither is wired in `Program.cs`. Browser apps can't call the API cross-origin, and auth endpoints have
no brute-force protection.

**Design.**
- **CORS:** a named policy whose **allowed origins come from config** (`Cors:AllowedOrigins`, a string
  array). It allows the headers the apps send — `Authorization`, `X-Tenant-Id`, `Content-Type` — the
  standard methods, and credentials. `app.UseCors(policy)` is placed **before** authentication.
  Dev default origins = the five frontend dev servers (their localhost Vite ports); prod origins via
  env/config. No wildcard-with-credentials (disallowed by the browser anyway).
- **Rate limiting:** ASP.NET Core built-in `AddRateLimiter`:
  - a **global** partitioned sliding-window limiter keyed by client IP (default ≈ 100 requests / 10 s),
    and
  - a **stricter named limiter** applied to `/v1/auth/login` and `/v1/auth/refresh` (default ≈ 5
    requests / minute per IP) as a credential brute-force guard.
  - `app.UseRateLimiter()` in the pipeline; rejected requests return **429** rendered through the same
    error envelope (`code: "rate_limited"`). Limits are config-driven so ops can tune without a rebuild.

**Acceptance.** A cross-origin browser request from an allowed origin succeeds with the right CORS
headers and is rejected from a disallowed origin; exceeding the auth-endpoint limit returns 429 with the
error envelope; the global limiter caps burst traffic.

### Item 6 — Refresh hardening (reload tenant / roles / platform)

**Problem.** `/v1/auth/refresh` re-issues the access token with a **hardcoded** `school.admin` role and
**null** tenant (`src/Sms.Api/Endpoints/AuthEndpoints.cs`). A platform (Catre) user silently loses
platform status and a tenant user loses correct role/tenant after a refresh — a privilege-correctness
bug.

**Design.**
- After validating the refresh token and resolving the `userId`, **reload the user record** and issue
  the new access token with the user's **real** `tenant_id`, `is_platform`, and roles.
- `dbo.Users` is RLS-protected, so the reload runs under a **system (platform) session** — the same
  pattern login already uses: `tenant.Set(null, null, isPlatform: true)` for the lookup, then issue the
  token from the DB values (not the lookup context).
- Requires a new proc `dbo.User_GetById @Id` + `AuthRepository.GetByIdAsync(Guid)`, plus roles from
  Item 7's `UserRoles_GetByUser`. Refresh-token rotation (revoke old, persist new) is unchanged.

**Acceptance.** Refreshing a platform user's token yields a token with `is_platform = 1` and that user's
real roles; refreshing a tenant user yields the correct `tenant_id` and roles from `UserRoles` — not the
hardcoded `school.admin`/null.

---

### Item 7 — Login reads roles from `UserRoles`

**Problem.** `/v1/auth/login` hardcodes roles (`platform.only` for platform users, else `school.admin`)
instead of reading the existing `UserRoles` table (`src/Sms.Api/Endpoints/AuthEndpoints.cs`).

**Design.**
- New proc `dbo.UserRoles_GetByUser @UserId` returning the user's `Role` rows +
  `AuthRepository.GetRolesAsync(Guid)`.
- Login issues role claims from `UserRoles`; `is_platform` continues to come from the `Users.IsPlatform`
  column. If a user has no rows in `UserRoles`, they receive no role claims (seeding users/roles is a
  Phase-1 concern) — the auth flow itself stays correct.
- Shares the reload/roles machinery with Item 6. Both procs ship in a **new append-only migration
  `M0004_Procs_Auth_Login.cs`** (existing migrations are immutable once applied), following the embedded
  `CREATE OR ALTER` pattern of `M0003`.

**Acceptance.** A login for a user with rows in `UserRoles` produces exactly those role claims; a
platform user still gets `is_platform = 1`; no roles are hardcoded in the endpoint.

## Architecture impact

- **No new tables, no schema change.** Two new read procs (`User_GetById`, `UserRoles_GetByUser`) over
  existing tables, in one new migration `M0004`.
- **`db/Sms.Migrations`** gains an executable entrypoint (library role preserved).
- **`Sms.Shared.Kernel`** gains `SecretsValidator` and `GlobalExceptionHandler`; `AuthRepository` gains
  `GetByIdAsync` + `GetRolesAsync`.
- **`Sms.Api/Program.cs`** wires: secrets guard, exception handler (first), CORS (before auth), rate
  limiter, health checks. Middleware order becomes:
  `UseExceptionHandler → UseSerilogRequestLogging → UseCors → UseRateLimiter → UseAuthentication →
  TenantResolutionMiddleware → UseAuthorization → endpoints`.
- **Endpoints** unchanged in surface; `login`/`refresh` internals updated; `/health/ready` re-pointed.
- **CI** gains a migrate-twice (idempotence) step.

## Testing

All TDD (failing test → implement → green), matching the Phase 0 discipline.

**Unit (`Sms.Tests.Unit`):**
- `SecretsValidator`: throws on empty / placeholder / < 32-byte key and on missing connection string;
  passes on a valid key + connection string.
- `GlobalExceptionHandler`: produces the snake_case error envelope with `code: "internal_error"` and no
  leaked detail.
- CORS + rate-limiter options bind from config as expected.

**Integration (`Sms.Tests.Integration`, real SQL Server, throwaway DB):**
- Migration **CLI**: running it against a fresh DB applies all migrations; a second run is a no-op
  (idempotent); missing connection string → non-zero exit.
- `/health/ready`: 200 when the DB is reachable.
- **Refresh hardening:** seed a platform user and a tenant user (+ `UserRoles`); assert the refreshed
  access token carries the correct `is_platform`, `tenant_id`, and roles for each.
- **Login roles:** seed a user with `UserRoles` rows; assert login emits exactly those role claims.

**Out of this pass (stays Phase 6):** TVP bulk, keyset pagination, extra covering indexes, OTLP/metrics
export, Redis/SignalR backplane, read replicas, RLS/RBAC penetration test, HSTS/HTTPS redirection.

## Definition of done

Build clean (warnings-as-errors); all existing + new unit and integration tests green against
`DESKTOP-TJL4SG6`; migration CLI proven idempotent in CI; API refuses to boot with a weak/placeholder
key; `/health/ready` reflects real DB reachability; CORS + auth rate limiting active; login/refresh
issue tokens from real user roles/tenant/platform. **Still no business endpoints** — the foundation is
now production-deployable.
